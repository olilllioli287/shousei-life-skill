# 交件、收件檢查與審查派工規則

## 規格審查與問使用者

- **規格冷審**：交由冷審者冷讀，只給規格與相關檔，不給對話歷史與主控看法；題目開頭貼 `templates/review-header.md`，再加問「規格有沒有寫得太寬、互相矛盾、漏寫不改的行為」。最多 3 輪，連兩輪重複同樣未解問題就停下交使用者決定。多個模型一致只算建議。
- **問使用者**：只有主控能問使用者；整合者與施工節點不直接問，把待決項目整理成清單交主控。技術取捨由主控照規則先決定（保護不放鬆、選最單純可靠的），真的要使用者拍板的才問。問的時候一次一題，寫白話說明、選錯會壞什麼或丟什麼、各選項優缺點與主控建議（標明只是建議）；沒回答的留在任務看板「提議」（沒有這工具時寫進 `TASKS.md`），不派工。

## 交件與抽樣重跑

- 交件附：檔案清單、建議 commit 訊息、怎麼測的、哪些沒實測、測試留下的副作用。
- 上層要真的讀改動，重點看會不會丟資料；有問題退回原對話補齊，不自己順手改。
- **抽樣重跑**：下層附了證據，上層不必全部重跑，但每次收件至少親手重跑或核對一項（例：發布後自己查版本號與簽章、抽查審查者引文是否真的在原檔）。
- 回報裡的說法要分「量到的／推論的／猜的」；下層自己能跑的檢查不丟回給上層或使用者代勞。證據只證明做到被驗的那幾件，不等於整件做好。

## 收件檢查表（主控／整合者）

1. **規格逐項判定**：完成（附檔名:行號）／部分／沒做／改了／無法驗證（附手動驗證步驟）。「改了相關程式」不算完成。
2. **驗收測試實跑數**：實際跑了幾題（預期幾題）；0 題算失敗，結束碼不是證據。
3. **篩選審查發現**：只是風格、指不出觸發的呼叫處或輸入、沒人要求的防禦、只是換個寫法、或要等未來還沒做的改動才會出事的假想風險，丟掉並寫理由；附有重現指令的發現由收件方重跑，確認真的失敗才留；同一個根因的多條合併；多個審查者獨立都找到的最可信；總結時寫每位審查者各被篩掉幾條、為什麼。
4. **版本與輪數上限**：審查看的版本＝要 commit 的版本；最多 3 輪，不收斂就停下回報「未收斂」。
5. **多審查者彙整**：多個審查者的結果分「都找到」「只有一方找到」，並標明誰沒跑完。

## 出題規則（驗收測試）

- **職責分離**：出題與寫程式分開；測試撰寫者只看規格與原始需求，不讀原始碼，也不與寫程式者共用同一個對話。
- **狀態變更矩陣**：動到刪除／封存／取代／還原這類分支時，出「種類 × 動作 → 該留下的資料」矩陣驗收測試，每格一題，沒對到測試的格子算最高級問題。
- **識別字變更**：改名或刪除識別字時，同步檢查舊驗收測試裡斷言「舊名不存在」的題是否還有效。
- **修 bug 實測**：修 bug 的驗收測試要附「修之前會失敗」的實測。

## 審查派工規則

- 審查進行中被審的檔不能再改。
- 派審查前確認施工已交件、不再動；收結果前確認每個審查者都回報或已停。

## 發布流程

1. 施工在自己的 worktree／分支改好並 commit，交件給整合者。
2. 整合者讀改動、只 commit 交件清單上的檔（不用 `git add -A`）。
3. 發布前必跑驗收測試；驗收測試沒過不打 tag、不推。
4. 發布腳本從 tag 的乾淨副本編譯、發布、安裝。
5. 已回報且等著要用的修正，修好就發布；小改動累積 3～5 件或收工時才發布。
