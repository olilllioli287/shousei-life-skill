# 審查題目範本

## 組裝規則

1. 派審查前確認施工已交件、不再更動被審檔案；審查期間被審檔案不能再改。
2. 只給材料（diff、規格、相關檔案），**不附作者說明與主控結論**。
3. 題目最開頭貼入 `templates/review-header.md` 全文。
4. 若為**開工前規格冷審**，在材料前加問：「規格有沒有寫得太寬、互相矛盾、漏寫不改的行為」。
5. 若為**第二家審查（額外審查者）**，在 `templates/review-header.md` 之後、材料之前貼入下方「第二意見附加規則」。

---

## 題目結構範本

```markdown
<貼入 templates/review-header.md 全文>

<若是第二家額外審查，在此貼入下方「第二意見附加規則」>

【待審材料】
- 規格：<貼入或附上規格路徑>
- Diff / 相關檔案：<貼入 diff 或檔案清單與內容>
```

---

## 第二意見附加規則

（給額外審查者使用；接在 `review-header.md` 之後、材料之前）

1. 只依照附上的 diff 與規格實際寫的內容判斷；不要從函式名、檔名，或沒附上的程式碼去猜它的行為。
2. 不要推測「這個改動可能弄壞別的地方」，除非你能指出 diff 裡具體受影響的呼叫路徑（檔名＋行號＋原文）。
3. 下面兩種不要列成發現：規格明文要求的行為；這次改動之前就已經存在、這次沒有碰到的問題。
4. 另外列一段「看起來像問題、但其實沒事」：寫出看起來可疑的地方，以及為什麼沒事（例如規格就是這樣定、上下文已經處理）。寧可放這裡，不要塞進發現清單湊數。
5. （額外審查者附加規則）每條發現的信心 0～10：9～10＝從看得到的程式直接證實觸發條件；7～8＝很可能但有一個前提沒看到；第二意見審查者另外只列 7 以上（6 以下不列）。
6. 不要報：缺註解、缺型別標註、命名與排版、未使用的 import，除非它真的讓程式出錯。
7. 用繁體中文寫說明；檔名、函式名、原文照抄不翻譯。
